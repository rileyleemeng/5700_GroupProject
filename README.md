# SRFT Phase 1 raw-socket version

This version keeps the raw-socket requirement and adds the missing Phase 1 items that were not finished in the earlier draft:

- manual IPv4 + UDP header construction with `SOCK_RAW`
- checksum validation at the SRFT layer
- sequence numbers + client-side reordering buffer
- cumulative ACKs
- retransmission on timeout
- **multithreaded ACK handling on the server**
- **sliding-window transfer** instead of pure stop-and-wait
- **end-to-end MD5 verification** between sender and receiver
- configurable local packet-drop test hook for retransmission testing

## Files

- `server.py`: raw-socket server with sliding window + ACK receiver thread
- `client.py`: raw-socket client with cumulative ACK + reorder buffer + MD5 verification
- `packet.py`: SRFT application packet encode/decode/checksum
- `raw_utils.py`: manual IPv4/UDP header building and parsing
- `server_report.txt`: generated by the server after a transfer
- `client_report.txt`: generated by the client after a transfer

## Run

Linux / AWS only, with sudo:

```bash
sudo python3 server.py <server_ip>
sudo python3 client.py <filename> <server_ip> <client_ip>
```

Localhost example:

```bash
sudo python3 server.py 127.0.0.1
sudo python3 client.py big.txt 127.0.0.1 127.0.0.1
```

## Useful options

### Server

```bash
sudo python3 server.py 172.31.0.10 --window-size 16 --timeout 0.4
sudo python3 server.py 127.0.0.1 --simulate-drop-once 1
```

### Client

```bash
sudo python3 client.py big.txt 172.31.0.10 172.31.0.11 --output downloaded_big.txt
```

## How MD5 verification works

1. The server computes the file MD5 before sending data.
2. After all DATA packets are sent, the server sends an `END` packet whose payload includes file metadata (`name`, `size`, `md5`, `chunks`).
3. The client reconstructs the file, computes its own MD5, and compares it with the sender MD5.
4. The client prints the result and saves it to `client_report.txt`.

A transfer should be treated as successful only when:

- the file is fully received,
- the local size matches the sender size,
- the local MD5 matches the sender MD5.

## AWS Phase 1 testing steps

These commands help you satisfy the AWS + packet-loss testing requirement from the project PDF.

### 1. Start the server on EC2 A

```bash
sudo python3 server.py 172.31.x.x --window-size 16 --timeout 0.4
```

### 2. Add packet loss on EC2 B (client machine)

```bash
sudo tc qdisc add dev eth0 root netem loss 3% delay 40ms
```

To remove it later:

```bash
sudo tc qdisc del dev eth0 root
```

### 3. Start the client on EC2 B

```bash
sudo python3 client.py big.txt 172.31.x.x 172.31.y.y --output downloaded_big.txt
```

### 4. Keep these artifacts for submission

- server terminal output
- client terminal output
- `server_report.txt`
- `client_report.txt`
- screenshots showing the `tc` command and a successful transfer under 2%–4% loss

## Notes

- Raw sockets usually require root privileges and are most reliable on Linux / AWS.
- This code still stays within Phase 1. It does **not** implement the Phase 2 PSK handshake or AEAD security layer yet.
- The client supports out-of-order buffering, and the server now sends multiple packets per RTT using a window.
